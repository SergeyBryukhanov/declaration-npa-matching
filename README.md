# Сопоставление таможенных деклараций и регулирующих НПА

RAG + LLM решение: для каждой из 151 декларации возвращает 10 наиболее
релевантных НПА (из 562) в порядке убывания релевантности.

## Установка

```powershell
py -3.11 -m venv venv        # ВАЖНО: 3.10-3.12, не 3.13/3.14 - см. диагностику ниже
venv\Scripts\activate
.\install.ps1                 # ставит requirements.txt + llama-cpp-python
                               # (CPU или CUDA - автоопределение по nvidia-smi)
python prepare.py             # ОДНОРАЗОВО, требует сеть: скачивает Qwen2.5-7B-Instruct
                               # (GGUF, ~4.7 ГБ) и intfloat/multilingual-e5-small (~0.5 ГБ)
                               # в ./models/. Это разрешённый заданием разовый шаг вне
                               # лимита запуска.
```

На Linux/macOS вместо `install.ps1`:
```bash
python3.11 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
pip install llama-cpp-python==0.3.35   # см. "Использование GPU" ниже для CUDA-сборки
python prepare.py
```

Если веса уже скачаны иначе - положите их в `models/qwen2.5-7b-instruct-q4_k_m.gguf`
и `models/multilingual-e5-small/` (пути задаются в `src/config.py`) и
`prepare.py` запускать не нужно.

### Использование GPU (CUDA)

`llama-cpp-python` использует GPU, только если сама его сборка скомпилирована
с поддержкой CUDA - обычный `pip install llama-cpp-python` ставит CPU-сборку.
`install.ps1` определяет версию CUDA через `nvidia-smi` и сам подбирает индекс
готовых wheel'ов:

```powershell
pip install llama-cpp-python==0.3.35 --prefer-binary `
    --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cu130   # CUDA 13.0
```

(`cu124`, `cu125`, `cu132` и т.д. - под другие версии CUDA; список - в
выводе `install.ps1` или в [README проекта llama-cpp-python](https://github.com/abetlen/llama-cpp-python#supported-backends)).

При запуске `run.py` в логах явно печатается, поддерживает ли установленная
сборка GPU-офлоад (`src/llm_rerank.py`, диагностика при инициализации), а
`llama.cpp` при загрузке модели (verbose-вывод) построчно показывает, сколько
слоёв реально ушло на GPU - не полагайтесь на одну лишь скорость.

**Известная проблема Windows CUDA-сборок**: у upstream-проекта бывали периоды,
когда официальные Windows CUDA wheels либо не собирались, либо ставились, но
не задействовали GPU (см. [issue #2079](https://github.com/abetlen/llama-cpp-python/issues/2079),
[issue #1543](https://github.com/abetlen/llama-cpp-python/issues/1543)). Если
диагностика в логе показывает, что GPU не используется, несмотря на успешную
установку CUDA-сборки - решение всё равно полностью рабочее на CPU (просто
медленнее); альтернативой может быть community-сборка с встроенными CUDA DLL,
например [ThongvanAlexis/llama-cpp-python](https://github.com/ThongvanAlexis/llama-cpp-python/releases)
(CUDA 12.6, Python 3.11, DLL вшиты в wheel - CUDA Toolkit ставить не нужно).

**Видеокарты старше Turing (GTX 10xx и старее, архитектура Pascal/Maxwell,
compute capability <7.5)**: начиная с CUDA Toolkit 13.0 NVIDIA убрала
поддержку этих архитектур - `cu130`/`cu132`-wheel на такой карте не заработает
никогда, независимо от драйвера (даже если `nvidia-smi` показывает
`CUDA Version: 13.x` - это лишь максимум, который поддерживает драйвер, а не
гарантия работы CUDA 13 тулчейна на конкретном GPU). Нужна сборка под CUDA
12.x (`cu121`/`cu124`/`cu126`) - как официальная через `--extra-index-url`,
так и упомянутая выше сборка ThongvanAlexis с вшитыми DLL.

## Диагностика проблем установки

Частые ошибки и их первопричины (собрано по опыту установки на Windows):

| Симптом | Причина | Решение |
|---|---|---|
| `numpy`/`torch` не собираются, ошибка Meson/компилятора | Python 3.13+ или <3.10 - нет готовых wheel | `py -3.11 -m venv venv`, см. "Установка" |
| `llama-cpp-python` не собирается (`CMake Error: CMAKE_C_COMPILER not set`) | Нет готового wheel под точную версию/платформу, pip уходит в сборку из исходников без компилятора | Ставить через `install.ps1` / `--extra-index-url .../whl/cpu` (или `/cuXXX`), НЕ из `requirements.txt` напрямую |
| `pip install -r requirements.txt` падает целиком, хотя часть пакетов "уже скачаны" | Транзакция pip атомарна - один упавший пакет откатывает всё | `llama-cpp-python` вынесен из `requirements.txt` в отдельный шаг именно поэтому |
| `ModuleNotFoundError` на `huggingface_hub`/`sentence_transformers` сразу после "успешной" установки | Предыдущая транзакция откатилась целиком (см. выше), но это не всегда очевидно из лога | `pip list`, чтобы проверить, что реально стоит |
| `ValueError: Path .../multilingual-e5-small not found` | `prepare.py` не запускался или не закончился | `python prepare.py`; `run.py` теперь и сам проверяет это перед стартом и печатает понятную инструкцию вместо traceback |
| `404` при скачивании GGUF | Неверные repo/filename для конкретного HF-репозитория (у разных мирроров разные соглашения об именах) | Использовать проверенный источник (см. `src/config.py`, `LLM_HF_REPO`) или передать свой через `--llm-repo`/`--llm-filename` |
| `ReadTimeoutError` на середине скачивания GGUF | Короткий таймаут по умолчанию на нестабильном соединении | `prepare.py` теперь сам ставит таймаут 120с и до 5 повторов с задержкой; при необходимости увеличьте `HF_HUB_DOWNLOAD_TIMEOUT` вручную |
| Долгий запуск без вывода в консоль | Раньше прогресс печатался раз в 25 деклараций | Теперь прогресс-бар (`tqdm`) на каждую декларацию, со временем на декларацию и статусом LLM/фолбэк |
| Прогон прервали (Ctrl+C) - страшно потерять результат | Раньше `predictions.csv` писался одним файлом только в конце | Теперь пишется построчно и сбрасывается на диск (`fsync`) сразу после каждой декларации - прерванный прогон не теряет уже посчитанное (файл, впрочем, не будет валиден по формату, пока не досчитаны все 151) |
| GPU не используется, хотя видеокарта есть | `n_gpu_layers=-1` ничего не даёт, если сама сборка `llama-cpp-python` собрана без CUDA | См. "Использование GPU" выше; `run.py` теперь логирует, поддерживает ли установленная сборка GPU-офлоад вообще |

## Запуск

```bash
python run.py --out ./out
```

Полностью офлайн, без сети. Читает `declarations.jsonl`, `regulations.jsonl`
и `tnved_knowledge.txt` из корня проекта (пути переопределяются флагами
`--declarations`/`--regulations`/`--tnved`). Пишет `out/predictions.csv` и
сразу сам проверяет формат (падает с понятной ошибкой, если что-то не так,
а не молча отдаёт битый файл).

Во время выполнения показывается прогресс-бар (`tqdm`) с временем на
декларацию и статусом LLM/фолбэк; `predictions.csv` дописывается и
сохраняется на диск (`fsync`) сразу после каждой декларации, а не одним
файлом в конце - если прогон прервать (Ctrl+C, сбой), уже посчитанные
декларации не теряются (сам файл, впрочем, не будет проходить валидацию
формата, пока не досчитаны все декларации до конца).

Перед стартом `run.py` сам проверяет, что модели скачаны (`prepare.py`
выполнен) и что версия Python поддерживается (3.10-3.12) - при проблеме
печатает понятную инструкцию вместо traceback.

Быстрая самопроверка пайплайна **без реальных моделей** (секунды, не для оценки
качества, только чтобы убедиться, что всё гладко склеено на конкретной машине):

```bash
python run.py --out ./out_smoke --dry-run
```

Отдельная проверка формата уже готового файла:

```bash
python -m src.validate --out ./out/predictions.csv \
    --declarations ./declarations.jsonl --regulations ./regulations.jsonl
```

Тесты (не требуют GPU/сети/весов, ~секунда):

```bash
python tests/test_pipeline.py     # без pytest
# или
pytest tests/                     # если pytest установлен
```

## Подход

### Почему не просто эмбеддинги / просто ключевые слова

Данные без разметки (`declarations.jsonl` явно указывает: "правильная
регуляция отсутствует"), значит нельзя ни обучить кросс-энкодер, ни
подобрать веса по метрике - решение полностью unsupervised, а качество
оценивается организаторами на закрытой разметке. Анализ текста НПА показал,
что релевантность часто зависит от **конкретных числовых порогов**
(диаметр, класс точности, мощность, чистота вещества), которых чистое
косинусное сходство не различает, а декларации и НПА написаны в разных
регистрах языка (свободный/технический текст декларанта vs формальный
юридический текст). Отсюда - гибридная архитектура с LLM-проверкой
критериев, а не одна лишь модель эмбеддингов.

### Пайплайн

```
Декларация (G31_1)
      │
      ▼
[1] Нормализация текста (регистр, ё→е, токенизация + лемматизация)
      │
      ▼
[2] Якорение через ТН ВЭД (src/tnved.py)
    ├─ точный substring-поиск по 13 145 листовым описаниям справочника
    │  (декларанты часто дословно копируют формулировку товарной позиции)
    └─ фолбэк: BM25 по тому же справочнику
    → top-5 кодов ТН ВЭД + их каноничный юридический текст
      │
      ▼
[3] Обогащение запроса = текст декларации + каноничный текст ТН ВЭД (top-2)
      │
      ▼
[4] Гибридный поиск по 562 НПА (src/retrieval.py)
    BM25 + dense-эмбеддинги (multilingual-e5-small), слияние через
    Reciprocal Rank Fusion → top-`npa_candidate_k` кандидатов (сейчас 10)
      │
      ▼
[5] LLM-реранк, один вызов на декларацию (src/llm_rerank.py)
    Qwen2.5-7B-Instruct получает: текст декларации + контекст ТН ВЭД +
    кандидатов НПА (`npa_candidate_k`) → возвращает JSON со score по каждому, явно
    предупреждён различать категориальное совпадение ("оба про подшипники")
    от подтверждённого (конкретный числовой критерий текстом подтверждён)
      │
      ▼
[6] Гарантия формата (src/pipeline.py::fill_to_top_n)
    Ровно 10 уникальных id: сначала валидные ответы LLM, затем добор
    оставшимися retrieval-кандидатами с заведомо более низким score.
    Невалидные/несуществующие id из ответа LLM отбрасываются.
      │
      ▼
out/predictions.csv
```

### Почему LLM вызывается один раз на декларацию (listwise), а не на пару

151 декларация × 562 НПА = 84 862 пары - при вызове LLM на каждую пару
это на порядки больше 30-минутного лимита. Один listwise-вызов на
декларацию с `npa_candidate_k` (сейчас 10) кандидатами - 151 обращение к модели, что укладывается
в бюджет времени даже на CPU с квантованной моделью (см. `RuntimeConfig`
в `src/config.py` - есть защитный `llm_cutoff_fraction`: если время
исполнения приближается к лимиту, оставшиеся декларации доранжируются
только гибридным retrieval-скором без LLM, чтобы гарантированно не
превысить лимит и не оставить декларации без ответа вовсе).

### Пропуск LLM для однозначных случаев (опционально, по умолчанию выключен)

LLM-вызов - ~11-13с на декларацию, всё остальное в пайплайне почти бесплатно
(retrieval ~0.02с). Если retrieval уже уверенно выделил лидера, LLM, скорее
всего, ничего не изменит в верхушке ранжирования - вызов можно сэкономить и
отдать это время тем декларациям, где он нужен. Правило "однозначности"
(`src/skip_rule.py`) требует одновременно: (а) лидеры BM25 и dense-поиска
**совпали** (два независимых сигнала), (б) косинусный отрыв лидера от второго
места не меньше порога, (в) BM25-скор лидера превышает второе место не менее
чем в N раз. Признаки берутся из сырых сигналов ретриверов, а не из
RRF-скора: тот зависит только от рангов и почти не отличает явный случай от
спорного.

**Пороги не задаются "на глаз", и по умолчанию пропуск выключен.**
Лексическая однозначность - не то же самое, что "LLM согласится": пример из
реального прогона - подшипники, лексически почти дословно совпадающие с
прецизионными НПА, где LLM осознанно занижает score. Поэтому три режима:

| `--skip-llm` | Что делает |
|---|---|
| `off` (по умолчанию) | LLM на всех декларациях. Признаки уверенности всё равно пишутся в `timing_debug.csv` |
| `shadow` | LLM на всех, но для каждой декларации фиксируется, совпали ли лидер и топ-3 retrieval с ответом LLM. Даёт полноценный `predictions.csv` **и** данные для калибровки за один прогон |
| `on` | Однозначные декларации реально пропускают LLM. Требует явных `--skip-min-dense-gap` и `--skip-min-bm25-ratio` - без них запуск отклоняется до загрузки моделей |

Порядок работы:

```bash
# 1. Один полный прогон с LLM на всех (бюджет времени снят только для этого прогона)
python run.py --out ./out --skip-llm shadow --time-budget-min 90

# 2. Подбор порогов по логу: сколько деклараций можно пропустить и как часто
#    на них LLM подтверждала лидера retrieval
python scripts/calibrate_skip.py out/timing_debug.csv

# 3. Боевой прогон с порогами из рекомендации скрипта (он печатает готовую команду)
python run.py --out ./out --skip-llm on --skip-min-dense-gap X --skip-min-bm25-ratio Y
```

Скрипт может честно ответить, что безопасной экономии нет (ни одна комбинация
порогов не даёт требуемого согласия на достаточном числе деклараций) - тогда
`on` включать не нужно.

**Ограничения этого подхода** (важно для интерпретации):
- Измеряется согласие с **текущим пайплайном** (ответами LLM), а не с
  эталонной разметкой - её у нас нет. Систематические ошибки самой LLM
  скрипт не увидит.
- Пороги подбираются на тех же 151 декларациях, на которых решение
  оценивается: при малой выборке возможен оптимизм. Поэтому рядом с долей
  согласия скрипт печатает нижнюю границу 95% доверительного интервала
  Уилсона.
- Для пропущенных деклараций `score` синтетический (строго убывающие значения
  ниже шкалы LLM, как и у деклараций, обработанных без LLM из-за бюджета
  времени) и **не сопоставим** с LLM-оценками других деклараций - значим
  только порядок внутри декларации, что и требует задание. В логе и в
  `timing_debug.csv` (`skip_reason`) пропуск по правилу (`confident`)
  отличается от пропуска из-за нехватки времени (`budget`): первый не
  считается деградацией качества, второй - считается.

## Рассмотренные альтернативы

- **Pointwise LLM-реранк** (отдельный вызов на каждую пару декларация-НПА) -
  отклонено: не укладывается в лимит времени (см. выше).
- **transformers + bitsandbytes 4-bit** вместо `llama.cpp`/GGUF - даёт
  чуть более качественную генерацию и удобнее батчить, но практически
  привязан к CUDA и хуже предсказуем по потреблению RAM на CPU-фолбэке;
  для гарантии уложиться в 8 ГБ RAM на неизвестном железе выбран `llama.cpp`.
- **Готовый пакет BM25** (`rank_bm25` и т.п.) - заменён на собственную
  реализацию (~60 строк): меньше внешних зависимостей, полный контроль
  над кодом, ничего не теряется в качестве (классический Okapi BM25).
- **Более крупная эмбеддинг-модель** (`multilingual-e5-large`, `bge-m3`) -
  вероятно лучше по качеству семантики, но `multilingual-e5-small`
  выбрана ради гарантированного запаса RAM одновременно с 7B LLM
  (совокупно ≈5.2 ГБ активной памяти на модели, см. раздел "Бюджет
  памяти" ниже). Стоит попробовать увеличить модель, если целевая
  машина располагает большим запасом RAM, чем заявленный минимум.
- **Просить LLM вернуть только топ-10 кандидатов** (вместо оценки всех
  ~13-25 поданных) - опробовано и **отклонено** по результатам реального
  прогона: сокращало время генерации примерно вдвое (с ~21с до ~11с на
  декларацию), но заметно портило калибровку score. Конкретный пример -
  НПА про прецизионные подшипники (`NPA0556`), которые при формулировке
  "оцени всех кандидатов" корректно получали низкий score (0.25 -
  категориальное, но не подтверждённое совпадение), при формулировке
  "выбери топ-10" получили 0.85 на той же декларации и тех же кандидатах.
  Судя по всему, формулировка "выбери лучших" сама по себе смещает модель
  к более щедрым оценкам "раз я его называю - значит хороший", тогда как
  "оцени всех, включая заведомо слабых" вынуждает реально различать.
  Экономия времени вместо этого достигается снижением `npa_candidate_k`
  (меньше кандидатов на входе -> меньше объектов оценивать на выходе) без
  изменения самой постановки задачи модели.
- **Жёсткий фильтр кандидатов по разделу/группе ТН ВЭД** (например,
  "раздел про машины → рассматривать только decree 1661/1005") -
  сознательно НЕ сделан: прямого соответствия ТН ВЭД ↔ `decree_number`
  в данных нет (проверено - ни в `regulations.jsonl` нет ссылок на коды
  ТН ВЭД, ни в справочнике ТН ВЭД нет ссылок на номера наших НПА), а
  ошибочный жёсткий фильтр рискует убить recall. ТН ВЭД используется
  только как мягкий контекст для нормализации словаря и для LLM.
- **Примечания/пояснения ТН ВЭД** (легальные определения терминов по
  разделам/группам, тоже есть в `tnved_knowledge.txt`) - не парсятся и
  не используются в этой версии: потенциальный источник уточнения
  терминов, но требует дополнительного времени на разработку парсера
  сложной структуры файла. Отмечено как первое направление для развития.

## Допущения

1. **Значим только текст `G31_1`.** Остальные служебные поля декларации
   (`G011`, `G221`, `G32`, `G34`, `G42`, `GD0`, `GD00`, `ND`,
   `desc_extention`, `has_acceptance_docs`) в предоставленном наборе
   оказались константными, пустыми либо чистым порядковым номером
   (`G32` - перестановка 1..151) - проверено анализом всех 151 записей.
   Код их читает, но не использует в ранжировании. Если в закрытом
   тестовом наборе организаторов эти поля несут сигнал - потребуется
   доработка, но отсутствие такого сигнала не ломает пайплайн.
2. **`score` - относительная величина**, не откалиброванная вероятность.
   Важен порядок и строгая монотонность в пределах одной декларации
   (как и требует задание: "большее значение = более высокая
   релевантность"), а не абсолютные значения между декларациями.
3. **Категориальное совпадение ≠ подтверждённое совпадение критерия.**
   Явное допущение, зашитое в промпт LLM: если НПА требует конкретный
   числовой/качественный критерий (класс точности, изотопный состав,
   диапазон частот), а текст декларации его не подтверждает - ставим
   низкий score, даже при сильном лексическом пересечении. Обоснование -
   см. раздел "Сложности анализа" ниже (кейс с подшипниками).
4. **Ровно 10 НПА на декларацию всегда**, даже если по существу
   релевантных совпадений меньше или нет вовсе - жёсткое требование
   формата задания. Для таких деклараций итоговые кандидаты - "наименее
   плохие" по retrieval-скору с явно заниженным score.
5. **`tnved_knowledge.txt` - вспомогательный, не эталонный источник.**
   Используется только для нормализации словаря и контекста, не как
   таблица прямых соответствий (её в данных нет).
6. Скачивание моделей и (при необходимости) предвычисление кешей -
   разрешённый заданием разовый подготовительный шаг вне 30-минутного
   лимита запуска `run.py`.

## Компромиссы

- Listwise LLM-реранк экономит время ценой того, что модели сложнее точно
  откалибровать score каждого кандидата относительно остальных
  одновременно, чем если бы она видела их по одному.
- Малая эмбеддинг-модель (118M) - компромисс между качеством семантики и
  гарантированным запасом RAM под 7B LLM.
- Защитный cutoff по времени (`RuntimeConfig` в `src/config.py`): при
  приближении к лимиту оставшиеся декларации доранжируются только
  retrieval-скором без LLM. Порог адаптивный (см. `pipeline.py::run`) -
  прогнозирует по скользящему среднему последних LLM-вызовов, влезет ли
  ещё один, а не отсекает по жёсткой доле от общего бюджета. Это
  осознанно предпочтено варианту "не уложиться в лимит и не сдать
  результат вовсе"; в логах такие случаи явно помечаются.
- Пропуск LLM для однозначных случаев экономит время ценой риска, что LLM
  исправила бы retrieval именно там, где он выглядел уверенным. Поэтому он
  выключен по умолчанию, требует калибровки по данным и явных порогов
  (см. раздел выше).
- Примечания ТН ВЭД и section/group-эвристики не реализованы в v1 ради
  предсказуемого объёма работы - см. "Рассмотренные альтернативы".

## Бюджет памяти и времени

| Компонент | ОЗУ (приблизительно) |
|---|---|
| Qwen2.5-7B-Instruct, Q4_K_M GGUF | ~4.7 ГБ |
| multilingual-e5-small | ~0.5 ГБ |
| BM25-индексы (562 НПА + 13 145 ТН ВЭД) | < 0.2 ГБ |
| Python/интерпретатор/прочее | ~0.5-1 ГБ |
| **Итого** | **~6-6.5 ГБ** из лимита 8 ГБ |

Видеопамять GPU (если есть) используется дополнительно через
`n_gpu_layers=-1` в `LLMConfig` (offload максимума слоёв на GPU) и не
учитывается в лимите ОЗУ по условию задания.

По времени: BM25/ТН ВЭД-индексация и dense-эмбеддинги регуляций/ТН ВЭД -
секунды на CPU. Основная статья бюджета - 151 вызов LLM на реранк;
конкретная скорость зависит от железа проверяющего, поэтому и добавлен
защитный `llm_cutoff_fraction`.

## Сложности анализа, повлиявшие на качество ранжирования

- **Отсутствие разметки.** Нельзя посчитать метрику локально и подобрать
  веса/пороги численно - решение построено на общих принципах (гибридный
  retrieval + LLM-верификация критериев) и точечных ручных проверках, а
  не на оптимизации под скрытую метрику.

- **Разрыв словаря декларация↔НПА.** Декларации - разговорно-технический
  текст (бренды, артикулы, английские вставки), НПА - формальный
  юридический русский. Решается якорением через ТН ВЭД: официальная
  формулировка товарной позиции ближе по регистру языка к тексту НПА и
  используется для обогащения запроса.

- **Категориальное совпадение НЕ означает подтверждённую релевантность -
  конкретный найденный пример.** Декларация `...ПОДШИПНИКИ ШАРИКОВЫЕ,
  НАИБОЛЬШИЙ НАРУЖНЫЙ ДИАМЕТР КОТОРЫХ НЕ БОЛЕЕ 30 ММ...` лексически
  сильно пересекается с НПА `NPA0553`/`NPA0556` (тоже про шариковые
  подшипники), но эти НПА требуют **класс точности ISO 492 ≥2/4 и
  внутренний диаметр 12-50 мм** - критерий, которого в стандартной
  таможенной формулировке товара попросту нет и который обычный
  коммерческий подшипник, скорее всего, не удовлетворяет. Чистая
  лексика/эмбеддинги дали бы этой паре высокий score; в промпт LLM
  явно заложено правило снижать score в таких случаях (см. `SYSTEM_PROMPT`
  в `src/llm_rerank.py`).

- **Отсутствие прямого моста ТН ВЭД ↔ `decree_number`.** Проверено явно:
  ни в `regulations.jsonl` нет ссылок на коды ТН ВЭД, ни в справочнике
  ТН ВЭД нет ссылок на номера постановлений из нашего набора. Значит
  раздел/группа ТН ВЭД не может использоваться как надёжный фильтр -
  только как мягкий текстовый контекст (см. "Рассмотренные альтернативы").

- **"Пустые" декларации.** Часть товаров (например, обычная СХД на
  SSD-накопителях без явных подпадающих критериев) может не иметь ни
  одного по-настоящему релевantного НПА в списке из 562, но формат
  требует ровно 10 строк. Для таких случаев ожидается, что итоговый
  `score` будет заметно ниже, чем у деклараций с явным совпадением -
  это специально заложено в `fill_to_top_n` (fallback-кандидаты всегда
  строго ниже LLM-подтверждённых).

- **Ограничение модели ≤8B параметров и бюджет по времени/памяти.**
  Компенсируется architecture-level решениями (listwise вместо pointwise,
  небольшая эмбеддинг-модель, собственный BM25, защитный time-cutoff) -
  подробнее в разделах "Компромиссы" и "Бюджет памяти и времени".

## Известные ограничения / что можно улучшить дальше

- Не используются примечания/легальные пояснения ТН ВЭД (определения
  терминов по группам) - могли бы уточнить пограничные случаи.
- Нет эмпирической калибровки порогов "категориальное vs подтверждённое"
  совпадение в промпте LLM - сформулировано на основе анализа одного
  показательного примера (подшипники), не проверено на статистике из-за
  отсутствия разметки.
- Score из LLM не прогонялся через отдельную калибровку (temperature
  scaling и т.п.) - используется как есть.
- Пороги пропуска LLM (если включать) подбираются на тех же данных, на
  которых работает решение, и по согласию с ответами LLM, а не с
  эталонной разметкой - см. оговорки в разделе "Пропуск LLM для
  однозначных случаев".
- При очень медленном железе (см. `llm_cutoff_fraction`) часть деклараций
  может остаться без LLM-уточнения - это логируется, но не устраняется
  автоматически (например, повторной попыткой с меньшим числом
  кандидатов).

## Результат тестового прогона

Итог реального запуска на Google Colab (Tesla T4, CUDA 12.1, GPU-офлоад
подтверждён `llama_supports_gpu_offload() == True`), дефолтные настройки
(`python run.py --out ./out`, без `--time-budget-min`):

- **Все 151/151 деклараций получили полноценный LLM-реранк.** Адаптивный
  time-budget cutoff (`src/pipeline.py::run`) не сработал ни разу - запаса
  в 28.5 минуты из разрешённых заданием 30 хватило с небольшим остатком.
- **Итоговое время: 28.0 минут** (`Готово за 1680.5 сек`).
- LLM-реранк на декларацию: медиана 10.81с, среднее 10.87с; разброс узкий
  (p10=10.22с, p90=11.59с, максимум 12.87с) - без аномальных выбросов.
- Retrieval (BM25+dense) и якорение ТН ВЭД - медиана 0.02с каждый,
  пренебрежимо малы на фоне LLM (см. `out/timing_debug.csv` для полной
  разбивки по каждой из 151 декларации).

**Вариативность времени между прогонами - честное замечание.** На той же
конфигурации и том же типе GPU повторный прогон дал среднюю стоимость
LLM-вызова 13.4с вместо 10.9с (+23%): бесплатная T4 в Colab разделяемая, и
пропускная способность плавает. Адаптивный cutoff в этом случае сработал как
задумано - 123 декларации получили LLM, 28 обработаны только retrieval-ом, а
общее время осталось 28.0 мин (без cutoff все 151 при 13.4с заняли бы ≈33.6
мин, то есть превысили бы лимит). Запас против такой вариативности - снижение
`npa_candidate_k` (25 → 13 → 10) и, опционально, пропуск однозначных случаев.
Цифры выше и таблица калибровки ниже получены при `npa_candidate_k=13` в
прогоне, где все 151 получили LLM; после снижения дефолта до 10 их стоит
обновить повторным прогоном (время на вызов должно упасть, а калибровку
на тех же показательных декларациях - перепроверить).

**Проверка калибровки score** на трёх показательных случаях (подробнее - в
"Рассмотренные альтернативы", сравнение промпта "выбери топ-10" vs "оцени
всех кандидатов"):

| Случай | Наблюдение |
|---|---|
| Шариковые подшипники >30мм (не прецизионные) | НПА про прецизионные подшипники (класс точности ISO 492 ≥2/4) корректно получили низкий score 0.25 - категориальное совпадение распознано, но не подтверждено текстом |
| Система хранения данных на SSD | Все 10 кандидатов получили одинаково низкий score 0.05 - честный сигнал отсутствия реального совпадения, а не правдоподобная убывающая "лесенка" без содержательной опоры |
| Огнетушители (Галон 1211) | Топ-1 НПА - 0.85, с содержательной дифференциацией по остальным 9 - ожидаемо высокая уверенность при прямом текстовом совпадении с decree КЕЭК№30 |

**Честно об ограничении**: score заметно квантуется (наблюдались значения
0.05/0.10/0.15/0.25/0.50/0.65/0.70/0.85, а не непрерывная шкала). Внутри
одной "корзины" одинакового score порядок в выводе определяется устойчивой
сортировкой (детерминирован, воспроизводим), но не несёт дополнительного
содержательного смысла - это ожидаемо для LLM без специальной калибровки
уверенности и не противоречит требованию задания (нужен порядок и
монотонность, не откалиброванная вероятность).
